In programming, casing refers to the capitalization style used for naming variables, functions, classes, etc. 
Common casing styles include camel case, Pascal case, snake case, and kebab case


Camel Case => myVariableName
Pascal Case => MyVariableName  (start with Capital letter)
Snake Case => my_variable_name
Kebab Cas => my-variable-name
Flat Case => myvariablename
Upper Case => MY_VARIABLE_NAME

• Camel Case: Capitalizes the first letter of each word after the first word (e.g., myVariableName).  
• Pascal Case: Capitalizes the first letter of each word (e.g., MyVariableName). [1]  
• Snake Case: Separates words with underscores and uses lowercase letters (e.g., my_variable_name).  
• Kebab Case: Separates words with hyphens and uses lowercase letters (e.g., my-variable-name). 
• Flat Case: No capitalization or punctuation is used, simply concatenating all letters (e.g., myvariablename).
• Upper Case (Constant Case): All letters are capitalized, often used for constants (e.g., MY_VARIABLE_NAME).

==   ✏️=> (Loose Equality):
		Compares values after converting them to a common type if necessary. 
		May lead to unexpected results due to type coercion. 
		Example: "5" == 5 evaluates to true because the string "5" is converted to the number 5. 
===  ✏️=>(Strict Equality): 
		Compares both value and type directly, without any type conversion. 
		Provides more predictable and reliable results. 
		Example: "5" === 5 evaluates to false because the string "5" is not the same type as the number 5. 
		
		---------------
// = (equal to means value only)
let isEqual = 5 == '5'; // true (loose comparison)

// == (strict equal to means value + type)
let isStrictEqual = 5 === '5'; // false (strict comparison)

☑️ This diff contains a change in line endings from 'LF' to 'CRLF'.

it means Git detected that the file’s newline characters changed, even if the actual text stayed the same.

Different operating systems use different newline styles:

OS            | Line Ending   | Meaning
--------------|---------------|--------------------------------------
Linux/macOS   | LF (\n)       | Line Feed
Windows       | CRLF (\r\n)   | Carriage Return + Line Feed
---------------------------------------------------------------------

So Git is telling you:

The file originally used LF
The version you staged/committed uses CRLF
This creates a large diff, even though the text might not have changed.

----------
✅ Why This Happens
Common causes:
✔ 1. Your editor auto‑converted line endings
VS Code, Notepad++, IntelliJ, etc. may silently change LF → CRLF.
✔ 2. Git configuration is converting line endings
core.autocrlf or .gitattributes can trigger conversions.
✔ 3. The file was copied from Windows or a Windows tool wrote it
----------
✅ How To Fix It
Option 1: Convert back to LF inside your editor
Most editors show line ending type (bottom-right corner).
Choose: LF → Save file again.

Option 2: Tell Git to always use LF (recommended for cross-platform repos)
Add a .gitattributes file:
* text=auto eol=lf

Then normalize the repo:
git add --renormalize .
git commit -m "Normalize line endings"Show more lines

Option 3: Disable Git’s automatic CRLF conversion
For Linux/macOS users:
git config --global core.autocrlf input
For Windows users who want LF everywhere:
git config --global core.autocrlf false
